# 回归任务规格(盲对比用)

> 用途:把本批已完成的工作反推成**实现无关**的任务规格,交给另一个 coding agent 独立实现,再与本仓库现有产出做盲对比。
>
> 对应 git 区间:`6b11e97`(不含)→ `f8751cd`,18 个提交。
>
> 刻意不写目录名 / 模块名 / 函数名 / 技术选型 —— 只描述「要做成什么、必须满足什么约束、怎么算通过」。这样对比 agent 的产出才不会被现有实现牵着走。

---

## 产品背景(所有任务包的共同上下文)

一条产品分析流水线:输入「产品名 + 官网 URL」,驱动一个 AI coding agent 子进程,让它访问官网、发现并体验客户端(桌面/移动)、截图,最终产出一份中文分析报告(`report.md` + `metadata.json` + `screenshots/`)。已有一个 CLI 编排层(Python)和一套「业务规则文档」(skill)。本批任务在此基础上扩展。

下面拆成 5 个可独立交付的任务包。每个都能单独丢给对比 agent。

---

## 任务包 A:网页控制台前端

**目标**:做一个本地 Web 控制台,可视化这条流水线的运行。

**功能需求**
1. 任务列表:展示所有历史/进行中任务,支持按状态和分类过滤。
2. 新建任务表单:输入产品名 / URL / 可选下载链接,发起单次分析。
3. 批量导入:从队列文件(JSON)导入一批任务并下发。
4. 实时日志:以终端风格流式展示子进程输出,支持过滤/搜索。
5. 报告展示:渲染 Markdown 报告(含目录导航)+ 截图画廊预览。
6. 凭据管理面板 + 全局设置弹窗(后端契约见任务包 C)。
7. 完整的空 / 加载 / 错误状态。

**约束**
- 组件需按「功能域」组织,具备可维护的拆分粒度(避免出现单文件几百行的巨型组件)。
- 样式方案需组件级隔离。
- 通过一个统一的 API 客户端层与后端通信,不在组件里散写 fetch。

**验收**
- `npm run dev` 起得来,能连本地后端拉到任务列表。
- 大组件(日志面板、任务侧栏)有明确的子组件/数据模型分离。

**不预设**:目录命名、状态管理库、CSS 方案、组件树形状 —— 由实现者决定。

## 任务包 B:邮箱验证码自动注册

**目标**:当目标产品需要注册才能体验时,让 agent 能自助完成「邮箱注册 + 收验证码/验证链接」。

**功能需求**
1. 提供一个可被 agent 调用的工具:创建一次性测试邮箱、轮询收取验证码或验证链接。
2. 是否启用由上游配置开关控制;关闭时 agent 不得创建新邮箱。
3. 与编排层和规则文档串接:规则文档要说明何时允许注册、注册流程怎么走。

**硬约束(安全/合规,属于需求不是实现)**
- 禁止:手机号注册、绕过 CAPTCHA、邀请码破解、付费绑卡、营销邀请。
- 验证码/邮箱等 secrets **只能**返回给当前调用,**禁止**写进报告 / metadata / 日志。

**验收**
- 有不依赖真实网络的单元测试覆盖核心解析逻辑(验证码提取、链接提取)。

## 任务包 C:配置持久化 + 凭据安全存储

**目标**:让邮箱服务配置可持久化,让注册产生的账号凭据被安全保存、可跨同产品任务复用。

**功能需求**
1. 全局配置持久化(如邮箱服务商参数),后端提供读写 API,前端设置弹窗可编辑。
2. 凭据存储:写入操作系统级安全存储(非明文文件),带索引,支持 list / find / delete。
3. 凭据按「来源任务 + 产品」标注,同产品的后续任务可复用。

**硬约束**
- secrets 不进版本库、不进报告、不在 API 响应里明文回传给非必要场景。
- 读取已存凭据与「创建新邮箱」是两个独立开关:配置关闭时仍可读旧凭据,但不创建新账号。

**验收**
- 有 mock 掉真实安全存储和网络的单元测试。

## 任务包 D:Android 客户端分析能力

**目标**:当产品有 Android 客户端时,能在移动沙盒里安装 APK 并体验、截图。

**功能需求**
1. 一个移动端控制桥:启动沙盒、安装 APK、点击/滑动/输入/按键、截图、状态查询、销毁。
2. 与批量流程集成。
3. 规则文档新增 Android 分支:何时走 Android、APK 从哪来(只用官方来源,Google Play 只记录证据不从第三方镜像下载)、控制命令怎么用。

**硬约束**
- 移动端有独立触控语义,不得复用桌面沙盒的控制桥。
- 每步操作前后各做一次状态快照来校验动作落地(snapshot-before-and-after 不变量)。

**验收**:控制桥每条命令单步执行、输出结构化结果、可断点续跑。

## 任务包 E:后端目录重构为分层 `src` 布局

**目标**:把扁平的实现包重组为标准的 `src` 布局 + 独立入口脚本目录,用现代 Python 包管理器管理依赖。

**功能需求**
1. 实现代码迁入 `src/`,按依赖层次分子包(底层工具 → 配置 → 沙盒 → 分析编排 → 批量 → web)。
2. 所有外部入口收敛到一个 `scripts/` 目录(薄 shim)。
3. 引入 `pyproject.toml`(非包模式)+ lockfile;测试迁入后端内部并配好测试路径。

**硬约束(重构最易翻车处,属于验收项)**
- 依赖**单向无环**:底层包不得 import 上层包。
- 包内相对导入、跨包绝对导入,二者一致。
- 路径推导(仓库根、安装脚本位置等)必须随文件深度变化同步修正。
- **所有外部调用链同步更新**:hook 注册路径、规则文档里的命令路径、前端启动后端的脚本路径、README/贡献文档里的命令。
- 重构**不改行为**:原有 CLI 参数、子进程协议、任务状态机不变。

**验收**
- 入口 `--help` 跑得通,全模块可编译。
- 测试全过(用包管理器的运行环境,而非系统 Python)。
- 全仓搜不到旧包名的残留引用(迁移说明性文字除外)。

## 用法建议

- **盲对比**:把任意一个任务包整段(含「产品背景」)交给对比 agent,不给它看本仓库的 commit。它实现完后,拿对应任务包的「验收」逐条核对两边。
- **差异维度**:重点看
  1. 是否满足硬约束(尤其 B/C 的 secrets 不外泄、D 的 snapshot 不变量、E 的依赖无环);
  2. 拆分粒度和架构选择;
  3. 是否带测试。
